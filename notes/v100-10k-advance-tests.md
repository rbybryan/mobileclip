**问题**:主时钟(4×H100)被 6.6 天/轮卡着,而 `101vector`(8×V100)基本闲着。
**哪些东西可以现在就在 V100 + 那 1 万条抽样上先测掉,不用等 H100?**

本文按**每一项真正需要什么**分档,而不是按"重要性"排 —— 因为这台机器缺的不是算力,
是**数据**。先读 §0,它决定你能进哪一档。

## §1. A 档:只要权重(或什么都不要)—— 今天就能跑,不碰任何评测数据

这一档全部是 **CPU 或单卡、分钟级**,而且**不需要任何评测视频**。
它的价值是:把第五轮(§8)几条提案的**正确性风险**在花 H100 时间之前全部拆掉。

### A1 · 环境实况 + SDPA 可用性(10 秒)
命令见 [`COMMANDS.md`](../COMMANDS.md) **§3.13**。
**为什么要跑**:仓库多处按 `mobileviclip.yml` 的 torch **1.13.1** 推理,断言"SDPA 用不了、
P1 被环境卡住"。**那个环境哪台机器都不是**(本机 2.5.1+cu118)。
**判读**:`has SDPA = True` ⇒ P1 无环境阻塞;`arch_list` 只含 `sm_70` ⇒ 本机走
memory-efficient 内核(仍消掉 N×N 物化),**完整 Flash 要 sm80+,那是 H100 那边的事**。

### A2 · SDPA 替换的数学恒等性(10 秒,CPU)
复现脚本见 `COMMANDS.md` §3.13 第二段。本地已实测 `max|朴素 − SDPA| = 2.08e-16`
(float64,按本模型真实 stage-4 形状 N = T·H·W = 512、20 头)。
**判读**:< 1e-12 ⇒ 恒等,只是 roundoff。**这条在 V100 上重跑一遍就等于本机独立复核。**

### A3 · P11 门张量普查 —— 防的是本仓已经犯过一次的错(1 分钟,CPU)
探测脚本见 `COMMANDS.md` **§3.14** 的键名探测块。**期望 40 / 40 / 40**:
`token_mixer.layer_scale_1d`(时序 mixer)/ `token_mixer.layer_scale`(**空间** mixer)/
**块级** `layer_scale`(ConvFFN 门)。

> 🔴 **全模型 `layer_scale` 共 80 个 = 40 空间 + 40 块级。** 把两者混池**正是 §0.1 里
> `gate5` 分母取错、凭空造出 2.42% 的同一个坑**。这一步就是那个坑的护栏。
> ⚠️ 顶层 wrapper 键**不是** `model`(§3 开头那次静默 no-op 栽在这)——按 §3.14 那样先探。

### A4 · 🔺 P11 恒等塌缩的正确性单测(随机输入,CPU,~10 分钟写完)
**这是 A 档里最值钱的一项。** P11 的全部前提是:把一个块的 **3 个**门置零 ⇒ 该块**精确恒等**。
这件事**不需要任何评测数据**就能证明 —— 喂随机张量,断言输出 == 输入:

```python
# tests/ 里加一条;依据:RepMixer.forward:743-746 + RepMixerBlock.forward:1075
import torch
blk = <build one RepMixerBlock>          # 训练态,use_layer_scale=True
with torch.no_grad():
    blk.token_mixer.layer_scale_1d.zero_()   # 时序 mixer 残差门
    blk.token_mixer.layer_scale.zero_()      # 空间 mixer 残差门
    blk.layer_scale.zero_()                  # 块级 ConvFFN 门
x = torch.randn(8, C, H, W, dtype=torch.float64)   # T*B, C, H, W
assert torch.allclose(blk(x), x, atol=1e-12), "置零后该块必须是恒等"
```

**判读**:通过 ⇒ P11 的 40 块扫描可以放心上 GPU。**不通过 ⇒ 说明还漏了门,当场省下 40 次评测。**
⚠️ 记得 `set_num_frames(T)` 要先设,否则 reshape 会崩(`:1431`)。
另:**stage 4 的 4 个 `AttentionBlock` 门结构不同(`:1111-1188`)、§8 里明确标注未核** ——
顺手在这里核掉,它决定扫描是 40 块还是 44 块。

### A5 · 🔺 gate5-fused 的**空间** mixer 那一半 —— §8 明确标注"未验证"(~10 分钟)
`gate5-fused` 只量过**时序**核 `|w_1d − δ|`(结论:INT8 只抹掉 36.2% 通道,中位数在阈值
**1.57 倍以上** ⇒ P2 机制被证伪)。**配套那句"空间 mixer 只跑在 1–3 LSB / ~2 有效 bit"
至今没人量过**,而且鉴于时序那次估计错了 1–2 个数量级(假设 `|Δ|`=O(0.1–1),实际 ≈7.7),
**应当默认它也是错的,直到量出来**。

要量的量:对**空间**分支做同样的 `reparameterize_model()` 后取 `|w − δ|` 的分位数,
对比 INT8 round-to-zero 阈值 **3.937e-3**。⚠️ 用的是 **40 个 `token_mixer.layer_scale`**
那一支,**不是**块级那 40 个(见 A3)。
**判读**:中位数远低于 3.937e-3 ⇒ 原说法成立,空间 mixer 确实被 INT8 压到几个 LSB,
AC9(QAT>PTQ)拿回一个**新的**存在理由;中位数在阈值之上 ⇒ 与时序一样,该说法也作废,
**AC9 该埋了**。**纯权重统计,零数据,V100 上今天就能出。**

### A6 · channels_last 的等价性 + 时序分支那个静默拷贝陷阱(~30 分钟)
§8.3 P12 的头号嫌疑是**全仓无 `channels_last`**,但同时给了一条顺序约束:
**必须在删时序分支(round4-P1)之后再开**,因为 `:726-731` 的
`reshape → permute(1,3,4,2,0) → reshape` 链假定 NCHW 连续,`.reshape` 碰上 channels_last
会**静默插一次拷贝**。
**这条完全可以在 V100 上用随机输入验证**:同一份权重,NCHW vs channels_last 前向,
比对输出(应当只差 roundoff)**并同时数一下 `is_contiguous()` 翻转次数 / 用 profiler 数
`copy_` 内核**。
**判读**:输出等价但多出拷贝 ⇒ 顺序约束确认,P1 必须先行;输出**不等价** ⇒ 更严重,
说明有算子对 layout 敏感,H100 上开 channels_last 会静默改数值。
**注意**:这里量的是**正确性与拷贝数**,**不是加速比** —— V100 的加速比对 H100 没有外推力(§4)。

### A7 · 逐块 MACs / 分辨率曲线复核(随机输入,~20 分钟)
`torch.utils.flop_counter` 不需要数据。两件事一起做:
① 复核 §8.2 的结论 **每个 RepMixerBlock 都是 157.29 M MACs**(`3C²S` 在 C 翻倍/S 四分之一下
不变),44 × 157.29M = 6.921 G/帧 = 89.6%,应当与 §1 实测的 86.5% pointwise 份额对上;
② **顺手把 round4-P7 的分辨率 MACs 曲线免费拿到**:对 `img_size ∈ {128,160,181,224,256}`
各跑一次 —— 视觉塔**已核实与分辨率无关**(无绝对位置嵌入、`RepCPE` 是核不是网格、
head 是 `GlobalPool` mean),所以改 `img_size` **不需要插值也不需要重训**。
**判读**:①对不上 ⇒ §8.2 的推导有问题,P11 的前提要重审;②给出等像素前沿的**成本轴**
(精度轴还得等 C 档的评测)。

### A8 · 随机初始化下的导出 + 图规模 diff(CPU,零 GPU)
本项目自己的**成文规矩**:*任何效率主张,在拿到随机初始化变体的实测端侧数字之前,
不授权训练*(§3 检查 8)—— 因为**延迟不依赖权重值**。
`experiments/export_smoke.py` 已在本机跑通(ONNX + Core ML 在 T∈{2,4,8,16} 全 pass)。
可以**现在就**把这几个变体各导一次并 diff 节点数:基线(1581 节点)/ 删时序分支(1141)/
SDPA 版 / P11 剪若干块后 / 各分辨率。
**判读**:节点数与 layout op 占比(基线 340 = 21.5%)是**可以写进论文的效率证据**,
且完全不需要评测数据。⚠️ TFLite 那格仍被 `litert-torch` 需 torch≥2.6 卡住 ⇒
**别为它动本机 torch**(会让 8 卡在第一个 barrier 全崩),开独立 venv 补测。

### A9 · CPU 逐路径墙钟复核(~30 分钟)
§1 的 CPU 计时(时序分支 190 ms / 空间 dw3×3 68–98 ms / ConvFFN 790 ms,8 线程 T=8 B=1)
在 §6 里被明确标注为**"待复现"的顾问方数据**。本机复现即闭环。
**判读**:若时序分支仍占 mixer+FFN 墙钟的 ~18% 而只占 0.20% MACs ⇒ round4-P1 的
"删时序分支"论据独立坐实。

## §2. B 档:用得上那 1 万条(它有**字幕**,这点常被忘)

### B1 · 🔺 P13 的 BPE 词表覆盖率 —— 那 1 万条字幕正好是量它的材料(~10 分钟,CPU)
P13 的**估计**是:视频字幕域在 ≤32 token 下,**12–20k / 49,408** 个 token 就能覆盖 >99.9%
⇒ 嵌入表 25.3M → ~8M 参数。**这是估计,不是测量**,而**本机的 10k 字幕就能把它变成测量**:

```bash
python - <<'PY'
import json, collections
from models.backbones.internvideo2.mobileclip import ...   # 用仓库自己的 tokenizer
caps = [r["caption"] for r in json.load(open("<10k anno>.json"))]
cnt = collections.Counter(t for c in caps for t in tokenize(c)[:32])
tot = sum(cnt.values())
for k in (8000, 12000, 16000, 20000, 24000):
    print(k, f"{100*sum(v for _,v in cnt.most_common(k))/tot:.4f}% 覆盖")
PY
```

**判读**:某个 k 下覆盖 >99.9% ⇒ P13(b) 的裁词表落地,`25.3M → k×512` 参数,**零训练零 GPU**;
达不到 99.9% ⇒ 按 §8 的预登记**杀掉 P13(b)**,只留 P13(a) 的量化那半。
⚠️ 10k 是**中文抽样(`internvid_zh_*`)**,而训练/评测用的是英文字幕 ⇒ **覆盖率会偏乐观或偏悲观,
必须在结论里标明这是 10k-zh 口径**,全量英文语料上要重测。这条限制别省。

### B2 · 新开关的"链路 go/no-go" —— 这一档**官方**的职责
三档验证纪律里,**V100 / 10k 档的定义就是**:能跑通、loss 正常降、新参数收到梯度
(`ROADMAP.md` §验证分三档 ①)。所以每当第五轮的东西落成代码,都先在这里过一遍:

- **P1(SDPA)**:①`use_flash_attn=False` 时**逐位等于**现基线(house rule:off-path 必须
  bitwise 一致);②`=True` 时 loss 曲线与 off 基本重合;③`hasattr` 护栏在 1.13.1 CPU 配方下
  仍 import 得动。
- **channels_last / cudnn.benchmark / bf16→fp16 相关改动**:同上三条。
- 配置模板直接抄 `experiments/configs/pilot_10k_r0.py`(以及 `pilot_10k_r1*.py` 的写法)。

**判读**:三条全过 ⇒ 允许上 1M 档;任一条不过 ⇒ 当场修,**没浪费 H100**。

### B3 · SDPA 到底能不能抬掉 T=16 的显存天花板(1–2 卡,~1 小时)
§8.1 的**真正收益不是速度,是显存**:T=16、N=1024、20 头时,物化的注意力概率**就是**那
23.3 GB 峰值,而它卡住的是 **C2 自己的弹性 T 上界**(训练集合只敢保持 {2,4,8,16})。
在本机对 T ∈ {8,16} × {朴素, SDPA} 各测一次 `torch.cuda.max_memory_allocated()`。
**判读**:关心的是**比值**而不是绝对值 —— 若 SDPA 把 T=16 的峰值降下一大截,
就说明 H100 上"T 无上限"这条路是被一处 20 行的代码欠账挡着,而不是被算法挡着。
⚠️ V100 32GB < H100 80GB 且**无 bf16** ⇒ 绝对数**不可外推**,可能要减 batch 才跑得起来;
报数时把 batch 和 dtype 一起写上。

## §3. C 档:需要 MSR-VTT **视频**(先看 §0.0 的 `check_readiness` 那一行)

`msrvtt / k400 / ucf101 / hmdb51` 的 **anno 是齐的,只差视频**。一旦视频到位,
下面几项在本机就是**零训练、一晚跑完**的量级,而且**全部是当前 backlog 上最有价值的未认领项**:

| 项 | 内容 | 成本 | 依据 |
|---|---|---|---|
| **C-1** | **P11 的 40 块深度敏感度扫描** —— 每块置零 3 门 → 重评 MSR-VTT | ~1 GPU-小时 | `COMMANDS.md` §3.14 |
| **C-2** | **round4-P6** 聚合方式扫描 `agg ∈ {mean, max, LSE(τ), top-2}` —— `get_sim` **已经支持** `ndim==3` + `agg_method`,是死代码而非缺功能 | ~4 GPU-h | §2 P6 / §3 检查 6 |
| **C-3** | **round4-P7** 等像素分辨率前沿 128²/160²/181²/224²/256²(+ per-T BN 校准) | ~12 GPU-h | §2 P7 / §3 检查 7 |
| **C-4** | **§4 的判别实验**:单随机帧 / oracle 最佳帧 / mean-8 / mean-16 —— 一次性判定 T 的价值是**方差缩减**还是**覆盖**,这两者给出**相反**的聚合器处方 | 一下午(缓存特征) | §4 |

**两条强制纪律**(照抄,别省):
1. **删块 / 改分辨率都会移动下游每个 BN 的输入分布** ⇒ 评测前必须做一次**前向 BN 重校准**
   (`experiments/per_t_bn.py` 已有这套机器)。不做就是在量分布漂移。
2. **判读用配对 bootstrap**(`COMMANDS.md` §3.9),**两口径**(raw `ret_test_emb/` +
   DSL `ret_test/`)同向且 CI 不含 0 才算。**别套 ±1.6**,那是无配对带。
   ⚠️ 每臂**单独 `output_dir`**,否则 rank 文件互相覆盖(§3.0 踩过,三臂被冲掉一次)。

## §4. 🔴 V100 上**做不了**的(写在这里,免得有人白花一晚)

| 做不了的事 | 硬理由 |
|---|---|
| **P12 的 MFU 阶梯(整段)** | 要检验的 9.1821 s/it 与 MFU 0.67% **本身就是 4×H100 的数**;V100 **无 bf16**、fp16 峰值差约 8×、内核完全不同 ⇒ 在这里测出来**既证实不了也证伪不了**。已于 2026-07-30 明确否决过一次。**唯一例外是 A6**(正确性与拷贝数,不是加速比) |
| **任何"排方案序"的 A/B** | 三档纪律 ①:10k 档**排不了序** —— 评测饱和 + BN 混淆 + 二项 SE,且 **40M 参数在 1 万条上严重欠拟合,机制表达不出来**。排序是 1M 档(②)的职责 |
| **DiDeMo / ANet / SSv2-MC** | **连 anno 都没有**(在受限的作者 Google Drive 里)。SSv2 视频另有许可协议 |
| **C1 教师嵌入抽取的吞吐/成本切片** | 需要全量 InternVid 分片,本机 11 个一个都没有;且教师是 InternVideo2,V100 上跑它没有代表性 |
| **完整 Flash 注意力的加速比** | Flash 内核要 **sm80+**;V100(sm70)只能走 memory-efficient 内核。**显存收益是真的(B3),速度收益要到 H100 才算数** |
| **TFLite 那一格** | `litert-torch` 需 torch≥2.6,本机锁 2.5.1 是**为了 sm_70**。⚠️ **别动本机 torch** —— 会让 8 卡在第一个 barrier 全崩。开独立 venv 补测 |

## §5. 建议顺序(A 档一个下午能清掉大半)

1. **§0.0 `check_readiness.py`** —— 先知道自己在哪一档。
2. **A1 → A2 → A3**(共约 2 分钟)—— 把 §8.1 的环境结论和 P11 的门普查在本机独立坐实。
3. **A4 + A5**(半天)—— 两项都是 §8 里**明确标注未核**的东西,而且都零数据:
   A4 拆掉 P11 的正确性风险,A5 决定 **AC9 是拿到新理由还是该埋**。
4. **A7 + A8 + A9**(一天)—— 复核 §8.2 的推导、拿到 round4-P7 的成本轴、
   把"随机初始化即可测延迟"这条规矩真正用起来。
5. **B1**(10 分钟)—— 把 P13 从估计变成测量(记得标 10k-zh 口径)。
6. **A6 + B2 + B3** —— 等 P1/channels_last 落成代码之后再跑。
7. **C 档** —— `msrvtt` 视频一到位就开,**C-1 和 C-4 价值最高**。

> **一句话总结**:即使 MSR-VTT 视频一直不到位,**A 档 + B 档也已经能把第五轮(§8)里
> 三处"未核实"的地方(P11 的恒等塌缩、AC9 的空间 mixer 前提、P13 的词表覆盖率)全部结掉**,
> 而这三处每一处都可能改变要不要在 H100 上花时间。
