## §1. A 档:只要权重(或什么都不要)—— 今天就能跑,不碰任何评测数据

这一档全部是 **CPU 或单卡、分钟级**,而且**不需要任何评测视频**。
它的价值是:把第五轮(**§8–§11**)几条提案的**正确性风险**在花 H100 时间之前全部拆掉。

### A1 · 环境实况 + SDPA 可用性(10 秒)
命令见 [`COMMANDS.md`](../COMMANDS.md) **§3.13**。
**为什么要跑**:仓库多处按 `mobileviclip.yml` 的 torch **1.13.1** 推理,断言"SDPA 用不了、
P1 被环境卡住"。**那个环境哪台机器都不是**(本机 2.5.1+cu118)。
**判读**:`has SDPA = True` ⇒ P1 无环境阻塞;`arch_list` 只含 `sm_70` ⇒ 本机走
memory-efficient 内核(仍消掉 N×N 物化),**完整 Flash 要 sm80+,那是 H100 那边的事**。

### A2 · SDPA 替换的数学恒等性(10 秒,CPU)
复现脚本见 `COMMANDS.md` §3.13 第二段。本地已实测 `max|朴素 − SDPA| = 2.08e-16`
(float64,按本模型真实 stage-4 形状 N = T·H·W = 512、20 头)。
**判读**:< 1e-12 ⇒ 恒等,只是 roundoff。**这条在 V100 上重跑一遍就等于本机独立复核。**

### A3 · P11 门张量普查 —— 防的是本仓已经犯过一次的错(1 分钟,CPU)
探测脚本见 `COMMANDS.md` **§3.14** 的键名探测块。**期望 40 / 40 / 40**:
`token_mixer.layer_scale_1d`(时序 mixer)/ `token_mixer.layer_scale`(**空间** mixer)/
**块级** `layer_scale`(ConvFFN 门)。

> 🔴 **全模型 `layer_scale` 共 80 个 = 40 空间 + 40 块级。** 把两者混池**正是 §0.1 里
> `gate5` 分母取错、凭空造出 2.42% 的同一个坑**。这一步就是那个坑的护栏。
> ⚠️ 顶层 wrapper 键**不是** `model`(§3 开头那次静默 no-op 栽在这)——按 §3.14 那样先探。

### A4 · 🔺 P11 恒等塌缩的正确性单测(随机输入,CPU,~10 分钟写完)
**这是 A 档里最值钱的一项。** P11 的全部前提是:把一个块的 **3 个**门置零 ⇒ 该块**精确恒等**。
这件事**不需要任何评测数据**就能证明 —— 喂随机张量,断言输出 == 输入:

```python
# tests/ 里加一条;依据:RepMixer.forward:743-746 + RepMixerBlock.forward:1075
import torch
blk = <build one RepMixerBlock>          # 训练态,use_layer_scale=True
with torch.no_grad():
    blk.token_mixer.layer_scale_1d.zero_()   # 时序 mixer 残差门
    blk.token_mixer.layer_scale.zero_()      # 空间 mixer 残差门
    blk.layer_scale.zero_()                  # 块级 ConvFFN 门
x = torch.randn(8, C, H, W, dtype=torch.float64)   # T*B, C, H, W
assert torch.allclose(blk(x), x, atol=1e-12), "置零后该块必须是恒等"
```

**判读**:通过 ⇒ P11 的 40 块扫描可以放心上 GPU。**不通过 ⇒ 说明还漏了门,当场省下 40 次评测。**
⚠️ 记得 `set_num_frames(T)` 要先设,否则 reshape 会崩(`:1431`)。
另:**stage 4 的 4 个 `AttentionBlock` 门结构不同(`:1111-1188`)、§8 里明确标注未核** ——
顺手在这里核掉,它决定扫描是 40 块还是 44 块。

### A5 · 🔺 gate5-fused 的**空间** mixer 那一半 —— §8 明确标注"未验证"(~10 分钟)
`gate5-fused` 只量过**时序**核 `|w_1d − δ|`(结论:INT8 只抹掉 36.2% 通道,中位数在阈值
**1.57 倍以上** ⇒ P2 机制被证伪)。**配套那句"空间 mixer 只跑在 1–3 LSB / ~2 有效 bit"
至今没人量过**,而且鉴于时序那次估计错了 1–2 个数量级(假设 `|Δ|`=O(0.1–1),实际 ≈7.7),
**应当默认它也是错的,直到量出来**。

> 🔺 **规格已于 §10.4 大幅收紧,照它做,别自己造。** 关键是**别再用固定阈值** ——
> `gate5-fused` 当年拿 `|w−δ|` 去比一个固定的 3.937e-3,**隐含假设了每通道的 INT8 scale
> 分母恒为 1**,那正是它把结论说反的原因(§10.0:换成 LSB 单位后中位数是 **0.78 LSB**,
> 不是「存活」)。

**选哪 40 个**:`endswith("layer_scale") and "token_mixer" in k` —— 空间 mixer 那一支,
**它才被折进** `RepMixer.reparam_conv.weight`(`:766-777`)。另外 40 个块级 `layer_scale`
缩放的是 **ConvFFN 残差**,**从不折进任何 kernel**,与此事无关(见 A3)。
**重参数化之后按模块选,别按名字**:取同时具有 `reparam_conv` 和 `reparam_conv_1d` 的模块
(这样能排掉 stem / downsample / ConvFFN 里同样暴露 `reparam_conv` 的 MobileOneBlock)。
**两条断言**(当年就是少了它们才出的 40-vs-80 错):`n_modules == 40`、`Σ out_channels == 9920`。

⚠️ **两个会让你静默算错的形状坑**:空间核是 `(C,1,3,3)` ⇒ 归约要用 `amax(dim=(1,2,3))`,
**不是** `(1,2)`;`identity_kernel_like` 的 1 要放在 **`[1,1]`**,不是一维的中心下标。

**每通道要算的量**(`s_c = max|w_c|/127`,`ŵ_c = s_c·round(w_c/s_c)`):

| # | 量 | 用途 |
|---|---|---|
| 1 | `a_c = max|w_c|` | **真正的** per-channel scale 分母(gate5-fused 从没算过这个) |
| 2 | `n_c = 127·max|w_c−δ| / a_c` | 该支路占多少 **LSB**(尺度无关) |
| 3 | **`ρ_c = ‖ŵ_c − w_c‖₂ / ‖w_c − δ‖₂`** | **头条**:量化误差相对该支路本身的大小,三行,零假设 |

**时序核也照量一遍**,得到一个与空间可比、并取代那个 36.2% 的数。

**面板的预登记预测**:空间 λ ≈ 1.3e-2,若 |Δ| 与时序同量级(≈7.7)则 λ|Δ| ≈ 0.10 ⇒
**n ≈ 12 LSB、b_eff ≈ 4.7 bit、ρ ≈ 0.02–0.05** ⇒ 预测「空间 mixer 只有 1–3 LSB / ~2 bit」
**是保守方向上的错**。**决策表**:`ρ_中位 < 0.10` ⇒ 空间量化得很干净 ⇒ **埋掉 AC9 的
重参数化专属立论**,发一段机制说明(RepMixer 的恒等抽头是**未经 BN 的精确 δ**,与 RepVGG 不同,
所以它对量化是良性的);`0.10–0.35` ⇒ AC9 缩成一行部署规则(40 个 dw3×3 留 fp16 = 0.59% MACs),
**不做 QAT**;`≥0.35` ⇒ AC9 拿到新立论(**亚 2-bit 支路编码**),修法仍是 fp16-on-depthwise。
**纯权重统计,零数据,V100 上今天就能出。**

### A6 · channels_last 的等价性 + 时序分支那个静默拷贝陷阱(~30 分钟)
§8.3 P12 的头号嫌疑是**全仓无 `channels_last`**,但同时给了一条顺序约束:
**必须在删时序分支(round4-P1)之后再开**,因为 `:726-731` 的
`reshape → permute(1,3,4,2,0) → reshape` 链假定 NCHW 连续,`.reshape` 碰上 channels_last
会**静默插一次拷贝**。
**这条完全可以在 V100 上用随机输入验证**:同一份权重,NCHW vs channels_last 前向,
比对输出(应当只差 roundoff)**并同时数一下 `is_contiguous()` 翻转次数 / 用 profiler 数
`copy_` 内核**。
**判读**:输出等价但多出拷贝 ⇒ 顺序约束确认,P1 必须先行;输出**不等价** ⇒ 更严重,
说明有算子对 layout 敏感,H100 上开 channels_last 会静默改数值。
**注意**:这里量的是**正确性与拷贝数**,**不是加速比** —— V100 的加速比对 H100 没有外推力(§4)。

### A7 · 逐块 MACs / 分辨率曲线复核(随机输入,~20 分钟)
`torch.utils.flop_counter` 不需要数据。两件事一起做:
① 复核 §8.2 的结论 **每个 RepMixerBlock 都是 157.29 M MACs**(`3C²S` 在 C 翻倍/S 四分之一下
不变),44 × 157.29M = 6.921 G/帧 = 89.6%,应当与 §1 实测的 86.5% pointwise 份额对上;
② **顺手把 round4-P7 的分辨率 MACs 曲线免费拿到**:对 `img_size ∈ {128,160,181,224,256}`
各跑一次 —— 视觉塔**已核实与分辨率无关**(无绝对位置嵌入、`RepCPE` 是核不是网格、
head 是 `GlobalPool` mean),所以改 `img_size` **不需要插值也不需要重训**。
**判读**:①对不上 ⇒ §8.2 的推导有问题,P11 的前提要重审;②给出等像素前沿的**成本轴**
(精度轴还得等 C 档的评测)。

### A8 · 随机初始化下的导出 + 图规模 diff(CPU,零 GPU)
本项目自己的**成文规矩**:*任何效率主张,在拿到随机初始化变体的实测端侧数字之前,
不授权训练*(§3 检查 8)—— 因为**延迟不依赖权重值**。
`experiments/export_smoke.py` 已在本机跑通(ONNX + Core ML 在 T∈{2,4,8,16} 全 pass)。
可以**现在就**把这几个变体各导一次并 diff 节点数:基线(1581 节点)/ 删时序分支(1141)/
SDPA 版 / P11 剪若干块后 / 各分辨率。
**判读**:节点数与 layout op 占比(基线 340 = 21.5%)是**可以写进论文的效率证据**,
且完全不需要评测数据。⚠️ TFLite 那格仍被 `litert-torch` 需 torch≥2.6 卡住 ⇒
**别为它动本机 torch**(会让 8 卡在第一个 barrier 全崩),开独立 venv 补测。

### A9 · CPU 逐路径墙钟复核(~30 分钟)
§1 的 CPU 计时(时序分支 190 ms / 空间 dw3×3 68–98 ms / ConvFFN 790 ms,8 线程 T=8 B=1)
在 §6 里被明确标注为**"待复现"的顾问方数据**。本机复现即闭环。
**判读**:若时序分支仍占 mixer+FFN 墙钟的 ~18% 而只占 0.20% MACs ⇒ round4-P1 的

### 🔺 A10 · 已导出的四张 Core ML 图上量「延迟 vs T」—— **本清单里价值最高的一项**(~30 分钟)
出处 §10.5。**为什么最高**:整个量化方案的收益差 5 倍,取决于**一个从没量过的事实** ——
运行时**有没有把权重摊销到 T=8 这一批帧上**:
- 摊销了 ⇒ 总流量 ≈ 693MB 激活 + 72MB 权重 ⇒ 权重 INT8 只省 **4.7%** ⇒ 量化是**尺寸**杠杆;
- 没摊销(逐帧重读权重)⇒ 693 + 576 = 1269MB ⇒ 权重 INT8 省 **23%** ⇒ 是**速度**杠杆。

**而这台机器上 U1 导出冒烟已经跑过,T∈{2,4,8,16} 四张图就在手边。**
做法:对四张图各测稳态延迟,**画 latency vs T**。
**判读**:**严格线性 ⇒ 权重没被摊销**(截距≈0);**次线性且截距为正 ⇒ 摊销了**。
**顺带免费回答** §10.5 的「1 份权重 → N 张图」到底是不是问题。
⚠️ 这是 CPU/端侧导出图的量测,不是训练;与 §4 的「V100 测不了 MFU」不冲突。

### A11 · P15 批偏移时序混合的等价性(float64,CPU,~10 分钟)
出处 §11.1。P15 声称:时序 depthwise Conv1d **不需要任何 reshape/permute** ——
帧在 batch 维上是 `t·B + b`,所以它等于在**连续 NCHW 张量**上做三次带 batch 偏移的加权加。
面板在 CPU 上实测 `max|批偏移 − reshape/permute/conv1d| = 4.44e-16`。**本机独立复核一遍**:

```python
xv = x.view(T, B, C, H, W)
out = w[:,1].view(1,1,C,1,1) * xv
out[1:]  += w[:,0].view(1,1,C,1,1) * xv[:-1]
out[:-1] += w[:,2].view(1,1,C,1,1) * xv[1:]
out = out.reshape(T*B, C, H, W) + bias
```

**判读**:< 1e-12 ⇒ 等价成立 ⇒ **P15 严格优于 P3**(P3 仍需一次 clone,还会产出 §10.1 判为
ANE 快路径风险的大 dilation 卷积;P15 **一个 layout op 都没有**)。
**用途**:如果 P4 的对照实验需要时序分支活着,就用 P15 而不是删掉。

### 🔺 A12 · BN running stats 被更新两次(CPU,5 分钟)—— **正确性 bug,已复现**
出处 §11.3。`use_reentrant=False` 的梯度检查点会让反向重算**再跑一次 BN 训练态**,
于是同一个 batch 的 EMA 被应用两次。已独立复现(一步之后 `num_batches_tracked = 2`)。
**在本机对真模型确认一次**:跑一步,打印任一 BN 的 `num_batches_tracked`。

**判读**:`== 2` ⇒ 确认 ⇒ **本仓训过的每个 ckpt,BN 动量实际是 0.19 而不是 0.10**。
⚠️ **直接影响 C 档**:**P11/P7 强制的 BN 重校准那一遍必须 `with_cp=False` 跑**,
否则重校准本身也吃这个双更新。
⚠️ 讽刺但要记下:`use_reentrant=False` 当初正是为修 #316 的 DDP `marked as ready twice`
才加的 —— **一个修复引入了另一个 bug**,别直接回退。

### A13 · 逐块算子普查(dispatch trace,CPU,~30 分钟)
出处 §11.0。面板用 `TorchDispatchMode` 数出:每个 `RepMixerBlock` 前向 **55 个 aten 调用、
其中 33 个碰全激活张量、读写约 92 N**,且 **9 个 BN(BN2d×5 + BN1d×4)、7 个 conv、
2 个整张量转置 `clone`**。这是 §11 整条屋顶线订正的基础(训练步只有 ~15 FLOP/byte,
而 §8.2 的 60–240 说的是**重参数化后的推理图**)。
**本机复核**(CPU、随机输入、零数据即可),并顺便打印那两个 `clone` 的 **源 stride**。
**判读**:若 stride 里出现 `B·C·H·W` 量级的跨度(stage-1 = 41.9MB)⇒ §11.1 的
「一个 warp 的 32 条 lane 读 32 个相隔 41.9MB 的地址」成立 ⇒ 该分支确实是访存灾难。

## §2. B 档:用得上那 1 万条(它有**字幕**,这点常被忘)

### B1 · 🔺 P13 的 BPE 词表覆盖率 —— 那 1 万条字幕正好是量它的材料(~10 分钟,CPU)
P13 的**估计**是:视频字幕域在 ≤32 token 下,**12–20k / 49,408** 个 token 就能覆盖 >99.9%
⇒ 嵌入表 25.3M → ~8M 参数。**这是估计,不是测量**,而**本机的 10k 字幕就能把它变成测量**:

```bash
python - <<'PY'
import json, collections
from models.backbones.internvideo2.mobileclip import ...   # 用仓库自己的 tokenizer
caps = [r["caption"] for r in json.load(open("<10k anno>.json"))]
cnt = collections.Counter(t for c in caps for t in tokenize(c)[:32])
tot = sum(cnt.values())
for k in (8000, 12000, 16000, 20000, 24000):
    print(k, f"{100*sum(v for _,v in cnt.most_common(k))/tot:.4f}% 覆盖")
PY
```

### B3 · SDPA 到底能不能抬掉 T=16 的显存天花板(1–2 卡,~1 小时)

## §7. 🔴 P1 的**效率**主张还没被测量 —— 训练用的删除 ≠ 导出时的删除

`disable_temporal_branch`(#404)把 40 个 `layer_scale_1d` 置零并冻结,于是
`x = x + 0·(mixer_1d − norm_1d)` **在数学上**恒等 —— 这对 1M 的**精度** A/B 是正确且充分的。

**但它删不掉图里的算子。** `mixer_1d` 与 `norm_1d` 照样被计算,只是结果被乘 0。
所以 §8.3 P1 那三个数 —— **440 个 ONNX 节点(27.8%)、80 次全张量转置、CPU mixer 路径 −18%**
—— **不会**因为这个 flag 而实现。要拿到它们,需要在 `RepMixer.forward` 里加一条
**结构性旁路**(`if self.disable_temporal: 直接跳过整条支路`),那份代码**目前不存在**。

**后果,按本仓自己的规矩:**

> §3 检查 8(成文规矩):*任何效率主张,在拿到随机初始化变体的实测端侧数字之前,不授权训练*
> —— 理由是**延迟不依赖权重值**,所以这个数**随时**能测,没有借口拖到训练之后。

⇒ **P1-trained 这条 1M 臂回答的是「删了之后精度掉不掉」,不是「删了之后快多少」。**
两个问题都要答,但**后者不需要等 15 小时的训练**,它现在就能测。

**该做的两步(按序):**

1. 给 `RepMixer.forward` + `experiments/export_smoke.py` 加结构性旁路开关,
   导一次基线与旁路版,**diff 节点数**。基线锚点已知 **1581 节点**(A8),
   §8.3 P1 声称旁路版是 **1141**。**对上 ⇒ 效率主张坐实;对不上 ⇒ 那三个数要重算。**
2. 之后再谈 P1-trained 的精度臂。

⚠️ **不要把这条当成拦住 H100 的理由** —— 精度臂本身是独立且有效的,
只是**报结果时必须把两件事分开写**,别让「精度没掉」被读成「效率已兑现」。
